Section 1

Healthcare Interoperability Foundations

Healthcare interoperability centers on exchanging clinical information safely across systems with different data models, message formats, workflows, and operational constraints. Reliable integration depends on understanding how standards behave in production, where data quality issues appear, and how pipelines preserve trust from source payload to analytics view.

HL7 v2 Messaging

HL7 v2 is a widely deployed hospital messaging standard. It is event-driven and usually pipe-delimited. Patient registration, admission, discharge, lab result, order, and scheduling events are commonly exchanged as HL7 messages between clinical systems.

This project now generates and parses synthetic ADT^A01 and ORU^R01 messages. It reads MSH for routing metadata, PID for patient identity, PV1 for visit context, OBR for order context, and OBX for lab or vital result values.

FHIR Resource APIs

FHIR is a modern healthcare interoperability standard built around resource-oriented APIs. Patient, Encounter, Condition, Observation, MedicationRequest, AllergyIntolerance, Procedure, and DiagnosticReport are examples of core resources.

FHIR commonly uses REST and JSON, which makes it easier for data engineers to treat healthcare integration like API ingestion: request resources, validate payloads, normalize nested fields, and load curated tables.

HL7 v2 vs FHIR

HL7 v2 is commonly implemented as event/message processing. FHIR is commonly implemented as resource-oriented API integration. HL7 v2 remains heavily used inside hospitals because it powers long-running operational interfaces. FHIR is common for modern app integration, patient access, interoperability APIs, and analytics-friendly exchange.

A real environment often has both. An interface engine may receive HL7 v2 messages from an EHR, transform them, and expose a FHIR-style API or downstream analytics feed.

Healthcare ETL Requirements

Healthcare data often requires normalization even when the source API is available. Patient references may be missing, codes may be absent or inconsistent, timestamps may use different formats, and related resources may arrive in separate calls. A production-quality pipeline needs raw traceability, validation, curated models, audit logs, and quality checks.

For analytics, raw FHIR is usually too nested. Teams often flatten it into tables such as patients, encounters, conditions, observations, medications, and procedures.

Codes and terminology

FHIR resources often carry clinical codes. LOINC is common for lab and vital observations, SNOMED CT is common for clinical conditions and findings, RxNorm is common for medications, and ICD-10-CM is common for diagnosis and billing contexts.

Terminology preservation is important because the same display text can vary across systems. Analytics views should retain code, display, system, units, and timestamps wherever possible.

SMART on FHIR and OAuth

Many EHR FHIR APIs use OAuth through SMART on FHIR. The core idea is that an app gets authorized with a client ID, scopes, redirect URI, and an access token. The token determines which patient, user, and resources the app can access.

The current implementation uses public and synthetic data sources. The extraction layer is structured so OAuth-backed FHIR access can be added without changing the curated data model.

Epic on FHIR sandbox path

The project includes Epic on FHIR configuration placeholders for sandbox base URL, client ID, redirect URI, and SMART scopes. The active deployment keeps authentication disabled, but the code exposes the expected configuration contract through the local API.

The documented next step is an OAuth authorization-code flow that obtains an access token, calls Epic FHIR resources such as Patient, Observation, Encounter, and Condition, and reuses the existing normalization and quality-checking logic.

Privacy, security, and compliance thinking

HIPAA compliance depends on organizational controls, policies, contracts, infrastructure, risk analysis, monitoring, and incident response. This project focuses on application-level safeguards that support a compliance-aware operating model.

The application defaults to synthetic data, blocks PHI mode unless explicitly enabled, logs patient detail access, keeps ETL audit records, and uses curated minimum-necessary views instead of exposing raw clinical bundles in the UI.

Operational Analytics Layer

The dashboard is designed around questions that integration and clinical data teams commonly need to answer: which patients have risk signals, which resources are incomplete, which observation codes are flowing, and whether the latest ingestion run loaded expected records.

This keeps the project focused on data readiness, traceability, and clinical operations instead of static reporting.

Section 2

Project Technical Architecture

FHIROps Console is structured as a compact interoperability platform with separate ingestion paths, transformation logic, a relational store, analytics endpoints, compliance event logging, and an interactive dashboard.

Ingestion paths

The live path calls the public HAPI FHIR R4 endpoint and extracts Patient and Observation resources. This validates API-based FHIR ingestion against an external FHIR server while preserving a clear path to Epic on FHIR sandbox authentication.

The synthetic FHIR path generates Synthea-style bundles locally, then loads Patient, Encounter, Condition, and Observation resources. The HL7 path generates ADT and ORU messages, parses segments, and loads message/result tables. Together, the paths cover modern FHIR REST integration and legacy HL7 v2 interface processing.

Raw-to-curated design

The pipeline keeps raw JSON files so the original FHIR payloads can be traced and replayed. It then extracts the fields needed for reporting into curated relational tables.

This follows a common integration pattern: land the source data, validate and normalize it, then serve analytics from curated tables instead of repeatedly parsing nested JSON in the dashboard.

Data model

The main tables are patients, encounters, conditions, observations, hl7_messages, hl7_results, etl_audit, and compliance_events. Patients are the center. Encounters represent visits. Conditions represent diagnoses or active problems. Observations represent labs, vitals, and measurements.

The model intentionally keeps patient_id links across tables so the dashboard can support patient-level drill-down and operational worklists.

Validation and quality checks

The project validates required identifiers and core fields before loading curated records. The dashboard then scores readiness with checks like patient reference present, clinical code present, observation value present, effective date present, and encounter link present.

These checks reduce downstream reporting risk when clinical records are present but incomplete.

Dashboard API

The local web server exposes JSON endpoints for summary metrics, analytics, patients, encounters, conditions, observations, compliance posture, patient detail, and pipeline execution.

The UI does not query SQLite directly. It calls API endpoints, which keeps frontend responsibilities clear and supports future service-layer expansion.

Interactive UI logic

The dashboard includes interactive workflows rather than static charts. KPI cards and chart rows filter the resource browser. Selecting a patient opens the Patient 360 view. The worklist highlights risk signals such as elevated A1c or blood pressure based on observation values.

The result is an operational view for care-readiness, data-quality review, and patient-level drill-down.

Compliance posture implementation

The app defaults to DATA_CLASSIFICATION=synthetic and ALLOW_PHI=false. Patient detail views and dashboard events are written to compliance_events. ETL runs are written to etl_audit with source mode and load counts.

These controls do not replace enterprise compliance requirements. They establish application-level guardrails, auditability, minimum-necessary data exposure, and clear production-readiness boundaries.

Design decisions

SQLite keeps the project portable. Python keeps the ETL layer explicit and inspectable. Static HTML/CSS/JavaScript avoids unnecessary frontend framework overhead. Synthetic FHIR data limits PHI risk. The dashboard is built around operational questions instead of vanity metrics.

The design prioritizes practical integration judgment: focused tools, clear data contracts, meaningful quality metrics, and a defined path from local validation to production hardening.

Production hardening roadmap

Production hardening includes OAuth for Epic or another EHR sandbox, role-based access control, TLS, encrypted storage, secrets management, job scheduling, retry handling, structured logging, monitoring, and deployment behind an authenticated app gateway.

Additional scope would include FHIR resources such as MedicationRequest, AllergyIntolerance, Procedure, DiagnosticReport, and Immunization, plus terminology normalization and downstream data contracts.

Capability coverage

The project covers healthcare API ingestion, FHIR resource parsing, JSON normalization, HL7 v2 message parsing, SQL modeling, data quality scoring, audit logging, compliance-aware application design, interactive dashboard workflows, and patient-level operational analytics.

It uses public and synthetic data by default and separates local validation behavior from the additional controls required for real clinical data.
